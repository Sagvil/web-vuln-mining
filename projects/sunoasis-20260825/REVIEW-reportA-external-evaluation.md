# 外部评估记录：报告 A 撰写质量评审（2026-08-26）

> 来源：第三方评估者对报告 A（PbootCMS API 鉴权失效）的撰写评审。
> 归档用途：作为报告 A 的评审留档与后续报告撰写的方法论参照。

## 核心总结（一句话）

漏洞报告不是展示"我拿到了多少资料"，而是用最小、可复核、可脱敏的证据，
证明一条明确的"缺陷 → 未授权行为 → 实际影响"链路。
这也是报告 A 最值得保留和推广的写法。

## 一、报告 A 的证据链为什么比较扎实

报告 A 不是只说"接口可能存在鉴权问题"，而是形成了多组控制变量和闭环证据。

| 环节 | A 中的证据 | 能证明什么 |
|---|---|---|
| E1 | 无认证参数被拒绝 | 服务端存在一个预期的认证边界 |
| E2 | 仅提交任意非空 appid=x 即返回业务内容 | 非空 appid 可以绕过前置认证检查 |
| E3 | timestamp=0、signature=deadbeef 仍然返回业务内容 | 时间戳和签名没有被有效校验 |
| E4 | cms/form 返回历史人才推荐记录 | 可读取非公开业务数据 |
| E5 | cms/addmsg 接受安全测试数据 | 存在未授权写入 |
| E6 | 写入后的数据可再次读取 | 完成"写入成功 → 数据入库 → 回读确认"的闭环 |

其中最重要的是 E1/E2/E3 的控制变量设计：同一接口、同一请求方式、只改变认证
参数；先建立拒绝基线；再证明任意非空 appid 放行；最后用明显错误的签名和过期
时间戳证明关键鉴权字段没有真正生效。这比单独提交一张"返回了数据"的截图有说服
力得多。

## 二、报告 A 最推荐的写作结构

1. **标题只写一个根因**：`www.sunoasis.com.cn API 鉴权校验失效导致非公开人才
   推荐数据泄露（并可未授权写入业务表单）`；不要把未验证影响（后台接管、服务器
   控制、高危）混入标题。
2. **简要描述只回答四个问题**：哪个资产；哪个接口/功能；什么认证边界失效；
   造成什么已验证影响。
3. **基本信息独立简洁**：厂商、受影响域名、API 入口、漏洞类型、风险等级建议
   （用"中危起报"而非强制等级）、测试时间、测试边界、是否需要认证。
4. **根因分析写"观察到的行为"**，不伪装源码结论：
   - 用"黑盒行为显示 / 已验证接口存在 / 根因推测为 / 不代表所有路由"；
   - 避免"源码确定只判断 appid / PbootCMS 所有版本都有 / 所有 API 都可以绕过 /
     一定运行某个具体版本"。

## 三、复现步骤格式（每步固定五要素）

1. 请求；2. 预期结果；3. 实际结果；4. 结论；5. 对应证据编号。

- 注意：**HTTP 200 ≠ 请求成功**，必须看业务字段（code=0/1、是否返回业务数据、
  记录数变化、成功消息）。
- 用"任意**非空** appid"而不是"任意 appid"。
- 明确标注 timestamp=0 为明显过期值、signature=deadbeef 为故意构造的错误值、
  两者都不是页面复制的有效认证材料；不暴露真实 signature 或 API secret。

## 四、影响部分写成"闭环"

- 影响一（PII 读取）：写字段类别、记录数量、时间范围；不写真实值；原始 JSON
  不上传；审核需要时经平台私密渠道提供局部脱敏片段。
- 影响二（写入）：强调"匿名写入成功 → 数据进入业务表 → 后续读取确认"闭环；
  明确只写入 1 次、假数据+安全标记、无批量、未修改删除其他数据、建议厂商清理。

## 五、风险等级表达

当前证据支持中危定位（保密性+完整性+业务可靠性三方面同时受损）；不把未验证
内容（批量导出全库、账户接管、后台登录、命令执行、服务器控制、全部路由通用
绕过）计入等级。稳妥写法："当前证据足以支持中危定位；若平台确认可批量读取更
大范围个人信息或覆盖更多高敏感接口，可结合实际影响重新评估。"

## 六、六层证据栈（通用框架）

| 层级 | 要回答的问题 | A 中的对应内容 |
|---|---|---|
| 资产归属 | 目标是不是厂商的资产？ | 域名、官网、厂商证明 |
| 认证边界 | 正常情况下应该被什么拦截？ | 无参数基线被拒绝 |
| 绕过行为 | 哪个最小参数改变导致放行？ | appid=x、错误签名、过期时间戳 |
| 业务响应 | 服务端实际返回了什么？ | code=1、记录内容、写入成功 |
| 影响闭环 | 能不能证明数据真的被读取/写入？ | cms/form 读取、cms/addmsg 写入、回读确认 |
| 范围边界 | 没有验证什么？ | 未批量、未覆盖全部路由、未做后台接管 |

缺一层，报告通常都会变弱。

## 七、B 验证带来的通用经验

1. **当前证据和历史证据必须分开**：历史归档（13 条路径/119 条枚举）用过去时；
   当前状态只写实测内容（当前 filesId=19 元数据仍可匿名读取；当前 filesId=115
   路径经受限 Range GET 返回 206；当前只读首 512KiB 未保存完整文档）。
2. **证明文件暴露不一定需要上传完整文件**：Range GET 关键结果（206 +
   Content-Type + Content-Range 完整对象长度 + 首 8 字节 %PDF-1.7 + 无 Cookie +
   未跟随重定向 + 只读前 512KiB）足以证明"路径返回 PDF、暴露完整长度、非 HTML
   错误页、不需要认证"，无需把完整内部文档带回或上传。这是处理内部文档/配置
   文件/备份文件时可复用的最小化方法。
3. **不能为了增强说服力而无限扩大测试**：优先顺序 = 一个明确对象 → 一个最小
   请求 → 一个可重复响应 → 一个最小影响闭环 → 停止。

## 八、最容易导致报告失分的写法

1. 只写 HTTP 200 → 必须结合业务 code、响应内容、记录数或成功消息。
2. 单接口结论扩大到全部接口 → 写明"本次在 cms/search、cms/form、cms/addmsg
   完成验证，未对全部路由逐一测试"。
3. 历史证据写成当前状态 → "测试窗口曾确认 13 条路径"而非"当前可下载 13 个文件"。
4. 上传完整内部文档或个人信息 → 首页局部截图+大小+Content-Type+PDF 头+页数+
   哈希；路径 hash 脱敏；敏感材料仅经平台私密渠道提供。
5. 用"高危"替代证据 → "当前已验证匿名读取和匿名写入；账户接管、后台登录、
   服务器控制未验证，不纳入影响结论"。
6. 把两个不同漏洞合并 → 不同子域/不同接口/不同根因/不同修复方案，分开提交、
   互相交叉引用。

## 九、提交前通用检查清单

- 标题只描述一个明确根因；
- 简要描述 3-5 句说清资产、缺陷和影响；
- 详细细节含准确请求方法、路径、参数、响应；
- 至少一个拒绝/正常行为基线；
- 至少一个放行/异常行为对照；
- 业务影响通过读取、写入、回读或文件头闭环；
- 没有把单个对象扩大成全部对象；
- 没有把历史证据写成当前状态；
- 没有上传真实个人信息、Cookie、Token、API secret 或完整内部文件；
- 脚本不含凭据、不批量枚举或修改数据；
- 截图能同时看到请求、目标、状态和结论；
- 证据矩阵每一项对应正文或附件；
- 修复建议针对根因而非泛泛"加强安全"；
- A/B 分开提交并互相注明独立性；
- 不自动点击最终提交，保留人工审核环节。

## 十、最值得长期复用的报告模板（14 步）

1. 结论摘要；2. 基本信息；3. 测试时间、资产归属和范围；4. 正常行为基线；
5. 最小绕过请求；6. 异常响应和业务结果；7. 影响一；8. 影响二；
9. 当前证据与历史证据区分；10. 未验证事项；11. 风险等级依据；
12. 修复建议；13. 证据索引；14. 脱敏和测试边界。

核心写作模型：
无认证参数被拒绝 → 任意非空 appid 放行 → 错误签名和过期时间戳仍放行 →
非公开数据可读 → 安全测试数据可写 → 写入结果可回读 → 因此形成鉴权失效、
信息泄露和业务数据污染闭环。链条完整、克制、可复核，比堆叠截图或强调
"高危"更有说服力。
